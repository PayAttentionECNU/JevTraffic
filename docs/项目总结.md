# JevTraffic 项目总结（v1–v6）

更新：2026-11-06 · 代码：`main` @ `a3329c5`（GitHub `PayAttentionECNU/JevTraffic`，本地与服务器已同步）

## 0. 一句话结论

用 Jev 式"类型化决策"（单次前向、读选项字母的概率，不生成文本）做信号控制是可行的。从 UniTSA 蒸馏出的 **0.5B Jev 学生在留出路口上平均通行时间 48.4 s，优于教师 UniTSA（50.1 s）、MaxPressure（53.9 s）和全部 RL 基线**，单次决策 4.6 ms（GPU，CUDA graphs）。RL 继续训练后在训练路口上最好（37.3 s），在留出路口上与蒸馏模型持平（48.5 s）。在特殊事件上，Jev 的事件预案把特种车延误降低约 30–40%。

## 1. 项目目标与约束

**目标**：把 Jev（TypeSafe 的 "System One" 类型化决策模型）的思想用到交通信号控制上。模型接收状态和一个类型化问题（选择题 / 打分 / 是非），只做一次前向，直接输出各选项的概率。和生成式 LLM 智能体（"System Two"，先写推理再解析答案）相比，它的优势是：不会产生无效输出，单次决策更便宜，并且自带置信度，可以用来做门控和升级处理。

**约束**：
- 不调用官方 Jev API。决策器是开源实现（`jevtraffic/decider.py`，参照 open-alternative-jev 的 separate 模式），底座为 Qwen2.5-Instruct（0.5B / 1.5B / 7B）。
- 服务器 `root@202.120.87.207 -p 50030`，目录 `~/zzy/JevTraffic`。平时只用 GPU 6、7；v5、v6 两轮获准使用 0–7。
- 服务器磁盘几乎满（剩约 12 GB）：`ulimit -c 0`（禁止 core dump），及时清理输出。pip 安装一律加 `--no-deps`（直接 pip 曾拉入 torch cu130，弄坏 GPU 队列）。
- 服务器不能访问 GitHub，代码用 rsync / git bundle 同步。长任务一律用 `scripts/screen_run.sh` 挂在 screen 里。
- 只在用户要求时才 commit / push。

## 3. v1：USTBench / CityFlow

**设置**
- 环境：USTBench 的信号控制任务（CityFlow；杭州 4×4，济南 3×4）。每 30 s 决策一次，黄灯 5 s，3600 s 共 120 步。
- 指标：ATT（平均通行时间）、AWT（平均等待时间）、AQL（平均排队长度），计算方式与 USTBench 一致。
- 数据划分：训练文件 `hangzhou_real`、`jinan_real`、`jinan_real_2000`；留出文件 `hangzhou_real_5816`、`jinan_real_2500`。
- 控制器：
  - 规则：FixedTime / MaxQueue / MaxPressure
  - 参考上界：Rollout-greedy（在仿真里试探 4 个相位）
  - 生成式 CoT（vLLM）
  - Jev 的各种变体：
    - 状态：`jev-raw` 用 USTBench 原文，`jev-typed` 用结构化状态
    - 问题：`jev-score` 对每个相位打 0–9 分
    - 去偏和门控：`perm2/4` 置换选项顺序，`gate τ` 低置信时回退 MP

**零样本（Qwen2.5-7B，ATT 秒）**：MP 为 317 / 335 / 276 / 268 / 261；生成式 CoT 为 323–341，每决策约 1.9 s；Jev-typed 为 741–1300。零样本 Jev 与 MP 的一致率只有 3–17%，置信度却约 0.97（严重过度自信）。主要原因是位置偏置（偏向选项 A）和直行偏置。选项置换去偏和门控都无效。

**微调（三阶段，LoRA r=16，只在受限的选项字母 softmax 上算损失，每个样本随机打乱选项顺序）**
- 数据：在训练文件上跑 MP，加 ε ∈ {0, 0.1, 0.25, 0.5} 的扰动 × 3 个种子，共 5.6 万个样本，附 4 个相位各自 30 s 的反事实 rollout 代价。
- 阶段 1，蒸馏 MP（CE 损失）：留出文件上与 MP 一致率约 90%，ATT 比 MP 低 0.3%，约 56 ms/决策。
- 阶段 2，回报加权（soft target）和 DPO：DPO + 门控最好，ATT 比 MP 低 0.6%。上限本来就很小：rollout-greedy 也只比 MP 好 1.2%。另外 AWT 被抬高。
- 阶段 3，温度校准：蒸馏模型 T≈0.95，本来就接近校准；回报加权模型 T=0.52（欠自信）；DPO 模型 T=3.86（过度自信）。单一温度即可把 ECE 压到 0.02–0.07，之后 τ=0.6 的门控才可用，回退 7–15% 的决策，额外改善 0–0.3%。

**附带发现**：USTBench 的 `_selection_to_signal_code` 相位顺序与路网定义不一致（它把 ELWL 和 NTST 对调了）。这可能是论文里 LLM 成绩偏差（Qwen2.5-7B ATT 820）的原因之一。我们按路网顺序实现。

详见 [results/RESULTS.md](../results/RESULTS.md)。

## 4. SUMO 实验平台（v2–v6 通用）

- **平台**：SingleTSCBaselines（SUMO + TransSimHub），共 12 个真实路口 × easy/normal 两种路网 × 5 种需求模式（low_density、high_density、fluctuating_commuter、increasing_demand、random_perturbation）。一个 episode 1000 s，每 5 s 决策一次，黄灯 3 s，约 150–200 次决策。
- **划分**：
  - 训练路口（9 个）：Beijing_Beihuan、Beishahe、Changjianglu、Gaojiaoyuan、Pinganli、Yongrunlu，Chengdu_Chenghannanlu、Guanghua，Tianjin_zhijingdao。
  - 留出路口（3 个）：France_Massy（3 相位）、SouthKorea_Songdo（4 相位）、Hongkong_YMT（4 相位）。
  - 留出模式：random_perturbation。
- **分组**：seen = 训练路口 × 4 种训练模式；pattern = 训练路口 × 留出模式；junction = 留出路口 × 全部 5 种模式。
- **事件**：
  - `none`：无事件。
  - `event_1`：官方事件集。
  - `random:1`、`random:2`：两组随机事件，每组 1 起事故封道加 1–3 辆特种车（救护车、警车、消防车）。
- **指标**：ATT（SUMO tripinfo 的 duration，秒）。特种车单独统计 timeLoss。
- **种子**：最终表格全部用 SUMO 种子 0、1、2（3 个种子）；验证集用种子 100，与测试种子不重叠。
- **控制模式**：v2 为 `choose_next_phase`（选下一个相位）；v3 起为 `next_or_not`（保持 / 切换，与 UniTSA 一致）。最长绿灯 45 s 时由安全层强制切换。

## 5. v2：7B Jev + 上下文智能体 + 特殊事件 + 长期记忆

**架构**：
- 规则化的 ContextAgent 每步运行（O(1)，不调用 LLM），维护最近 5 步的短期记忆。
- 只在触发条件满足时才向 Jev 提一个"情况"问题。触发条件包括：绿灯不放行、V2X 发现特种车、排队突增、饥饿、连续低置信。
- 事件预案：
  - 特种车：绿灯优先，最多 30 s，优先级 消防 > 救护 > 警车。
  - 事故封道：把封闭车道从状态里排除，并发出通知（Notifier 写 JSONL）。
- 长期记忆：按路口存储决策记录，可选择按天 / 按周微调路口 LoRA，只有在回放验证日上更好时才部署；`auto` 模式在共享模型已经足够好时不训练。

**结果**：
- **E1/E2，无事件**：7B Jev（蒸馏 MP）在 seen / pattern / junction 上为 39.5 / 39.9 / 52.3；MP 为 39.2 / 39.2 / 53.9。从 CityFlow 的 adapter 起步时留出路口为 51.5。
- **E3，上下文**：触发式只在 1.2–1.9% 的步上额外调用，每步 73–103 ms；每步都调用要 258–340 ms，ATT 也没有更好。
- **E4，特殊事件**：250 辆特种车全部识别。特种车 timeLoss 在 `event_1` 下从 30–31 s 降到 15.4 s，在随机事件下从 24–25 s 降到 13.8 s。封道检出：规则检测器 160/198，Jev（触发式）123/194。
- **E5，14 个模拟日**：共享模型已经优于 MP，周期微调没有一次通过验证，所以从未部署；`auto` 是合理的默认值。

## 6. v3：UniTSA 教师 + 小 Jev 学生

- **UniTSA**（IEEE TVT 2024）：PPO，运动 token Transformer，动作为保持 / 切换。我们训练了：
  - 一个跨 9 个训练路口的**通用模型**（2M 步，79 分钟）；
  - 在每个留出路口上从零训练的模型（300k 步）；
  - 从通用模型出发、在 6 个路口上逐路口微调的模型（各 300k 步）。
- **学生**：Qwen2.5-0.5B / 1.5B 加 LoRA，问题是"保持当前绿灯还是切换到下一相位"。
  - 训练信号：UniTSA 的动作概率作软目标，共 6.5 万条，加上 9.4 千条特殊事件问题。
  - 训练设置：LoRA r=16，学习率 2e-4，batch 16，1 个 epoch。
  - 状态格式：`full`（约 320 token）或 `compact`（约 220 token）。
- **离线与教师的一致率**：验证集 0.86，留出模式 0.86，留出路口 0.75。
- **结论**：
  - 0.5B 学生的 ATT 与 UniTSA 通用模型相差在 ±1.5% 以内；GPU + CUDA graphs 下单次决策 4.6 ms，batch 8 时每决策 2.5 ms，显存 1.3 GB。
  - 事件预案让特种车延误下降 30–40%。
  - 识别封道需要 full 状态。

详见 [results/RESULTS_v2_v3.md](../results/RESULTS_v2_v3.md)。

## 7. v4：更多基线、小样本预算、PPO

**基线（全部按通用模型方式训练，与 UniTSA 对齐）**：
- 算法：PressLight（pressure 奖励，MLP，历史 5 帧）、AttendLight（pressure 奖励，Transformer，历史 4 帧）、IntelliLight（等待奖励，MLP，VecNormalize），均来自 SingleTSCBaselines 的 DQN 实现。
- 训练：在 9 个训练路口上训练，各 2M 步。
- 适配跨路口的改动（`jevtraffic/rl_baselines.py`）：
  - 相位特征补零到 4 列（`PadPhases`），动作空间统一为 Discrete(4)（`PadActions`）；
  - `MaskedDQNPolicy` 屏蔽不存在的相位。这个修复之前，3 相位路口会卡在补出来的假相位上，ATT 达到 180–209 s。
- 规则基线：FixTime、Webster、SOTL、MaxPressure。

**小样本**：每个学习型方法在每个留出路口上用 1 / 10 / 50 个 episode 做适配，再在该路口的全部 10 个场景 × 事件上测试。

**Jev 的 PPO**（`scripts/rl_jev.py`）：
- 策略：switch 问题里 A/B 两个字母的 softmax。
- 参数化：蒸馏 adapter 合并进底座，再加一个新的 LoRA；KL 的参考策略就是关闭新 LoRA 后的模型。
- Critic：UniTSA 的价值网络。
- GAE；强制切换并入上一个转移；用 spawn 进程并行采样。

**v4 的问题**：
- RL 在训练中退化：训练路口 ATT 从 37.5 升到 38.5–39.9，KL 涨到约 0.13。
- 当时测得留出路口 51.5 s，比蒸馏模型差。这个数字后来发现受 Songdo bug 影响，见第 9 节。
- 小样本适配常常变差：UniTSA 50 个 episode 后从 51.0 变成 54.0；DQN 方法波动很大。

## 8. v5：重做 RL 和保守小样本

**RL 的改动**：
- **奖励（Little 定律）**：每个决策区间内进口道上的"车·秒"，再加 0.1 × 区间长度 × 平均累计等待，乘 0.01 缩放。用折扣回报的滑动标准差归一化，截断到 ±10。依据是：在需求给定时，路口内车辆越少，通行时间越短。
- **KL**：两组，0.2（run a）和 0.5（run b）；v4 是 0.05。
- **训练**：每组 200k 次决策，24 个采样进程，critic 先预热 5 轮，每 15 次更新存一个 checkpoint。
- **选择**：在验证集上选 checkpoint。验证集 = 9 个训练路口 × 4 个训练模式，SUMO 种子 100，共 36 个 episode，与测试组不重叠。`update0`（即起点）也是候选，所以选出的模型在验证上不会比不做 RL 差。
  - 结果：选中 run a 的 `update75`，验证 ATT 39.32 s，起点为 40.42 s。run a 的 9 个 checkpoint 里有 7 个优于起点。全部 20 个候选的分数在 [results/rl5/selection.json](../results/rl5/selection.json)。

**小样本适配的改动**：

| 方法 | 设置 | v4 | v5 |
|---|---|---|---|
| DQN 基线 | 学习率 | 1e-4 | 1e-5 |
| DQN 基线 | 每次训练的梯度步 | 每个 worker 一步 | 1 |
| DQN 基线 | 探索率 | 线性衰减 | 固定 0.05 |
| UniTSA | 学习率 | 1e-4 | 1e-5 |
| UniTSA | 每批数据的训练轮数 | 10 | 2 |
| Jev PPO | 学习率 | 2e-5 | 5e-6 |
| Jev PPO | 每批数据的训练轮数 | 2 | 1 |
| Jev PPO | KL 系数 | 0.05 | 0.5 |

- **验证门控**（`scripts/fewshot_gate.py`）：在目标路口上，用 4 个训练模式、种子 100 分别跑适配后的模型和零样本模型，只有适配后更好才部署。这保证小样本在验证上不比不适配差。v4 的小样本模型和结果另行归档。
- **补齐**：规则基线在随机事件下的 3 种子结果。

## 9. v6：DAgger、布局增强，以及 Songdo 命名 bug

**DAgger**（`scripts/dagger_collect.py`）：
- 做法：让学生自己控制信号，UniTSA 给学生遇到的每个状态打标签，只用训练路口和训练模式。
- 数据：两轮，每轮 144 个 episode，约 2.1 万条。第 1 轮用 v3 学生采样，第 2 轮用第 1 轮的学生采样。
- 学生在训练路口上与教师的在线一致率为 0.86。

**布局增强**（`sumo_prompts.augment_switch`）：把所有进口道方位整体旋转同一个随机的 90° 倍数，并打乱运动行的顺序；50% 的 switch 样本做增强。UniTSA 的方向特征是转向类型（直 / 左 / 右），不是罗盘方位，所以旋转后教师标签仍然成立。

**训练**：与 v3 相同的配方和有效 batch 16，改为 4 卡或 8 卡 DDP，每个学生约 30–45 分钟（v3 单卡要 3.5 小时）。

**Songdo bug（本轮最重要的发现）**：
- 现象：逐路口分析显示，所有改动（增强、DAgger、RL）的退化几乎都集中在 SouthKorea_Songdo。增强后的学生在 Songdo 上 79.9 s，与教师一致率只有 0.42。
- 原因：Songdo 整体旋转了约 45°，4 个进口道方向是 48°、117°、228°、299°。固定 90° 的罗盘分区把它们命名成 `north`、`north-2`、`south`、`south-2`，文本状态里两个真实方向被写错了。
- 修复（`sumo_env.compass_names`）：按路口旋转分区，取能让每个进口道名称唯一的最小角度。已在仿真中逐一验证，其余 11 个路口的文本状态与修复前完全一致，因此训练数据和所有学生都不受影响，只需重跑 Songdo。
- 重做（`scripts/v6c_songdo.sh`）：重跑 Songdo 上所有 Jev 变体（3 种子），重训 Jev 在 Songdo 上的 3 个小样本 RL 模型（它们是在错误名称下训练的），重跑验证门控。旧结果归档在服务器 `results/sumo/runs_badnames/`。UniTSA、DQN 和规则基线不读文本状态，不受影响。

- **RL 版本**在训练路口上最好（37.3 s），在留出路口上与蒸馏模型持平；加上事件预案后，在 event_1（训练路口与留出模式）和随机事件（训练路口）下最好。
- **DQN 通用模型**（IntelliLight、PressLight）在训练分布内很强，但在留出路口上崩溃（88–104 s），泛化能力差。

## 11. 主要经验与踩过的坑

1. **状态表示比训练技巧更重要**。Songdo 的命名 bug 一度让 RL 看起来"泛化失败"，并让 DAgger 和增强看起来有害。逐路口分解 ATT，并检查学生与教师的在线一致率，是定位这类问题最快的方法。
2. **验证必须和测试分离**。RL 的 checkpoint 选择和小样本门控都只用验证种子 100，并把起点放进候选，这样从机制上保证"不比不做差"。
3. **零样本 LLM 读出不可直接用**：位置偏置和过度自信都很严重。蒸馏，加上随机打乱选项，再加温度校准，这三步缺一不可。
4. **短期回报和 ATT 不完全对齐**。v1 的回报加权和 DPO 抬高了 AWT，v4 用等待奖励的 RL 也会漂移。v5 改用 Little 定律奖励并加大 KL 后，训练才稳定。
5. **工程上的教训**：
   - SUMO 会把运行标签里的 ":" 解析成 host:port，已改为 "+"。
   - 3 相位路口必须屏蔽补出来的假相位。
   - libsumo 一个进程只能运行一个仿真。
   - 不要在 screen 运行脚本期间编辑该脚本（bash 是边读边执行的）。
   - 共享 GPU 时可能 OOM（v5 的一个 Songdo 任务因此失败后重跑）。
   - 服务器通过 HTTPS 推送 GitHub 会返回 403，改用 SSH。

## 12. 局限与下一步

- **v2 / v3 里其他 Jev 模型的 Songdo 数字**（7B v2 Jev、0.5B compact 学生、1.5B 学生、E5 模拟日）仍是修复前的结果，没有重跑；结论以本文第 10 节为准。
- **补充状态特征**：UniTSA 能看到每个运动的车道数、占有率和平均速度，而 Jev 的文本状态里没有。这是缩小剩余差距最有希望的方向。
- **更大的学生**：1.5B / 3B 学生，以及以 UniTSA 为参考的 KL、在更多样的需求下训练 RL。
- **事件指标**：v5 / v6 的特种车延误和封道检出只在 v3 做过完整统计，主表里只统计了 ATT。
- **任务结束后**恢复为只使用 GPU 6、7。
